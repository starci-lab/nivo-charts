# nivo-charts

Helm charts for **nivo** — one Kubernetes release per customer, per product. This repo holds the
charts only; the images they deploy are built and versioned in `nivo-backend`. The full business
and architecture spec they implement is `nivo-backend/biz.md`; where a chart and that spec
disagree, the spec wins and the disagreement gets called out in the chart's comments rather than
silently resolved.

## Products, one instance = one release

| chart | deploys | who uses it |
|---|---|---|
| [`charts/agentos`](charts/agentos) | a customer's OpenClaw sales/ops agent + n8n, behind a single controlplane | the customer's own end-customers, on Zalo/Telegram/WhatsApp |
| [`charts/expert-academy`](charts/expert-academy) | an expert's course site + a RAG chatbot over their own resources | the expert's learners |
| [`charts/mmo`](charts/mmo) | a generic MMO workload from an explicitly supplied image and service port, with optional ingress, persistence, and probes | control-plane maintainers validating the artifact; customer provisioning remains disabled |

Each installable chart uses `helm install <release-name> ./charts/<chart>` — never a shared release across customers.
biz.md section 1: subscription, RAM, the AI key, and data are all **per instance**, and "per
instance" here means per Helm release.

## Repository layout

```
charts/
  agentos/
    Chart.yaml          # pinned dependencies: postgresql, minio, qdrant
    values.yaml          # every configurable knob, each non-obvious one commented with WHY
    Chart.lock            # resolved dependency versions (checked in — do not hand-edit)
    charts/*.tgz           # vendored subchart archives from `helm dependency update`
    templates/
      _helpers.tpl          # name/fullname/labels/selector/hostname helpers
      ...                     # Deployment, Service, Ingress, hook Job, CronJob, RBAC — per-template
  expert-academy/
    Chart.yaml
    values.yaml
    Chart.lock
    charts/*.tgz
    templates/
      _helpers.tpl
      ...
  mmo/
    Chart.yaml
    values.yaml          # generic runtime inputs; image repository, tag, and service port are required
    values.schema.json   # rejects missing or invalid required values before rendering
    templates/           # Deployment, Service, ServiceAccount, optional Ingress and PVC
.github/workflows/
  helm-validate-and-publish.yml   # lint + template on every PR, package + publish to GitHub Pages on main
```

## Why subcharts for the stores

`postgresql` and `minio` are the Bitnami charts (pulled over OCI from
`oci://registry-1.docker.io/bitnamicharts`); `qdrant` is the official chart
(`https://qdrant.github.io/qdrant-helm`). All three model their workload as a `StatefulSet`, which
matters because a `Deployment`'s default `RollingUpdate` starts the new pod **before** stopping the
old one — on an RWO volume that deadlocks, on RWX two processes now share one data directory. Rather
than re-solve that inside this repo, the stateful pieces are dependencies.

**Every dependency version is a tilde range pinned at the patch level** (`~18.8.0`, never `18.x.x`),
and **every image tag inside `values.yaml` is a frozen `bitnamilegacy/*` tag**, not Bitnami's own
chart default (`bitnami/postgresql:latest`). Bitnami's free-tier images moved to `bitnamilegacy` and
stopped receiving new tags there; a moving tag under a pinned chart version would let Postgres
change major version on a pod restart with nobody having touched a file, and it would make
`instances.image_versions` tracking (biz.md section 8) meaningless.

## No secret goes in a chart or its values

biz.md section 8: a value in Helm values survives `helm get values`, CI logs, and backend request
logs. The only credential accepted directly by `agentos` and `expert-academy` is the **single-use
bootstrap token**, passed at install time (`--set bootstrap.token=...`) and never written to a file.
Everything else — n8n, OpenClaw, MinIO, Postgres, Qdrant credentials — is generated on first boot by
the workload itself, or auto-generated by the Bitnami subchart into its own Kubernetes `Secret` when
the corresponding `values.yaml` field is left blank. MMO credentials must be referenced through
Kubernetes Secrets via `envFrom` or `env[].valueFrom`, never supplied as literal values. A chart that
would leak a credential is a defect even if it deploys cleanly — this repo is **public**.

## Quickstart (local cluster)

```bash
# resolve subchart dependencies (writes Chart.lock and charts/*.tgz — already checked in,
# re-run only after bumping a dependency version)
helm dependency update charts/agentos
helm dependency update charts/expert-academy

# validate
helm lint charts/agentos
helm template smoke charts/agentos --set bootstrap.token=dummy --set instance.name=demo --set instance.id=demo-id

# MMO is artifact-only and has no concrete production defaults. Supply representative
# non-secret values when validating it.
helm lint charts/mmo \
  --set-string image.repository=example.invalid/nivo/mmo \
  --set-string image.tag=ci-smoke-test \
  --set service.port=8080
helm template smoke charts/mmo \
  --set-string image.repository=example.invalid/nivo/mmo \
  --set-string image.tag=ci-smoke-test \
  --set service.port=8080

# install against a real cluster (context must already point at it)
helm install acme-spa-hanoi charts/agentos \
  --set instance.id=<instances.id from backend> \
  --set instance.name=spa-hanoi \
  --set bootstrap.token=<single-use token from backend> \
  --set bootstrap.backendUrl=https://api.nivo.vn
```

## Publishing

`.github/workflows/helm-validate-and-publish.yml` lints and template-smoke-tests every chart on
every push touching `charts/**`, then on `main` packages all three and publishes an `index.yaml` to
GitHub Pages — the same shape as `starci-lab/kani-k8s`'s single-chart workflow, extended to a
matrix of chart directories with chart-specific smoke values.
